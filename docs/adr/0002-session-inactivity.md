# Inactivité indépendante par session

Pour #103, chaque ligne refresh représente une session/appareil : son UUID `sid` reste stable quand le secret refresh tourne. Access et refresh consultent la dernière activité persistée, avec refus à `lastActivity + 7 jours <= maintenant` ; le champ historique `expiryDate` reste informatif, sans imposer de durée absolue à une session active. La version du compte continue de révoquer tous les appareils. Émission, rotation et activité prennent le verrou utilisateur avant toute écriture de session ; une activité terminant après expiration ne peut pas la réactiver.

L’activité pertinente est une réponse métier authentifiée 2xx sur POST/PUT/PATCH/DELETE ou une lecture GET portant `X-Session-Activity: true`. Les clients Angular émettent ce marqueur pour la première lecture dans la seconde suivant un click/keydown/input browser trusted ; chargement initial, SSR et appels `/auth` sont exclus. Cette courte fenêtre est une heuristique documentée : aucun polling n’existe actuellement ; un futur polling doit explicitement rester passif. La durée serveur ne fait jamais confiance à une date client, et le refresh seul ne compte pas.

V21 accorde aux credentials historiques encore valides sept jours depuis la migration, sans réactiver les refresh déjà expirés. Les JWT historiques sans `sid` partagent provisoirement une session de compatibilité par compte, car ils ne portent aucune identité d’appareil reconstructible ; dès rotation, les nouveaux JWT portent le `sid` de cette session, et les nouvelles connexions ont leurs propres lignes. Un compte sans ancien refresh reçoit aussi une ligne de compatibilité inaccessible par secret connu pour conserver son ancien access JWT jusqu’à son expiration normale. Cette concession bornée évite une déconnexion massive au déploiement ; elle ne s’applique pas aux comptes créés après V21.
