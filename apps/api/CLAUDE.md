# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

MeetStudent backend — a Spring Boot 3 (Java 21) REST API managing schools, programs, courses, accreditations, and a rating system, with JWT auth and role-based access control (PUBLIC / STUDENT / EXPERT / ADMIN).

## Repository workflow

Follow the repo-level branch policy in `../../CLAUDE.md`: start backend work from an up-to-date `dev`, create a short-lived working branch, and open its PR against `dev`. Do not open backend feature, fix, docs, chore, refactor, test, perf or CI PRs directly against `main`; `main` is updated only by a separate `dev` → `main` promotion PR.

## Commands

```bash
# Build and run all tests (unit + integration)
./mvnw clean verify

# Unit tests only (surefire: **/*Test.java)
./mvnw test

# Integration tests only (failsafe: **/*IntegrationTests.java)
./mvnw failsafe:integration-test failsafe:verify

# Run a single test class / method
./mvnw test -Dtest=UserServiceTest
./mvnw test -Dtest=UserServiceTest#methodName
./mvnw verify -Dit.test=UserControllerIntegrationTests -Dtest=skip -DfailIfNoTests=false

# Run the app locally (dev profile, hot reload via devtools)
./mvnw spring-boot:run

# Run with Docker — the compose file now lives at the repo root and brings up
# the whole stack (Postgres + API + Angular front). See ../../compose.yml.
(cd ../.. && docker compose up --build)      # full stack
(cd ../.. && docker compose up --build api)  # API + its Postgres only

# Hot-reloading API in Docker (devtools). Recompile on the host — from your IDE
# or `./mvnw compile` — and the container restarts in about a second.
(cd ../.. && docker compose -f compose.yml -f compose.dev.yml up --build api)
```

Swagger UI is at `http://localhost:8080/swagger-ui.html`. All endpoints are versioned under `/api/v1/...`.

The test naming convention is enforced by the build: unit tests must end in `Test`, integration tests in `IntegrationTests`, or they won't run.

## Architecture

Standard layered architecture under `src/main/java/com/bowe/meetstudent/`:

- **controllers/** — `@RestController`s; validate input, call services, map entities to DTOs via mappers, return `ResponseEntity<DTO>` or `Page<DTO>`. Annotated with Swagger docs (`@Tag`, `@Operation`, `@ApiResponse`). List endpoints are paginated with `Pageable`.
- **services/** — business logic, `@Transactional`. Services return entities; mapping to DTOs happens in the controller.
- **repositories/** — Spring Data JPA interfaces.
- **entities/** — JPA entities (subpackages `rates/`, `embedded/`).
- **dto/**, **mappers/** — API contracts and Entity↔DTO conversion (ModelMapper plus manual mappers in `mappers/implementations/`).
- **security/** — Spring Security + JWT (Auth0 java-jwt). Dual-token system: short-lived access tokens plus database-backed refresh tokens with rotation and revocation. Endpoints are secured by default; `WebSecurityConfig` holds the access rules. A custom `UserPrincipal` is the authenticated principal (also used by JPA auditing in `JpaAuditingConfig`).

Dependency injection is by constructor via Lombok `@RequiredArgsConstructor`. Prefer `var` for clearly inferred local variables.

### Database & migrations

- PostgreSQL in dev/prod (profiles: `application.yml`, `application-docker.yml`, `application-prod.yml`); H2 in tests.
- All schema changes go through Flyway SQL files in `src/main/resources/db/migration`, named `V<Version>__<Description>.sql`.
- **H2 compatibility:** never use `@Column(columnDefinition = "text[]")` — it breaks H2. Use `@JdbcTypeCode(java.sql.Types.ARRAY)` on `List<String>` fields instead.
- Media files (logos, diplomas, videos) live in `uploads/`; `MediaService` deletes files from disk when the owning entity is deleted or the file is replaced.

### Media & documents

Personal documents (diplomas, certificates, bulletins, presentation videos) are modeled by the `Media` entity (one row per stored file) with category-derived visibility and a verification status — they are **not** stored as string fields on `UserEntity` anymore.

- **Storage split:** public files (`SCHOOL_LOGO`, `SCHOOL_COVER`, `USER_PHOTO`) go under `uploads/public/` and are served statically (`/uploads/public/**`); private files (personal documents) go under `storage/private/` (`file.private-dir`), are **never** mapped statically, and are reachable only through `GET /api/v1/media/{id}` with an owner-or-admin check. Configure both via `file.upload-dir` / `file.private-dir`.
- **Service split:** `MediaStorageService` does low-level file I/O (atomic write via `.tmp` + `ATOMIC_MOVE`, load, delete, anti-traversal); `MediaService` does orchestration — role-gated upload, idempotency (`Idempotency-Key` header, deduped on `(ownerId, idempotencyKey)`), download authorization, moderation, and delete.
- **Categories & roles:** `MediaCategory` carries `getVisibility()`, `isModerated()`, `getAllowedUploadRoles()`, `isPersonalDocument()`. Personal documents are uploadable by `ROLE_STUDENT`/`ROLE_EXPERT`/`ROLE_ADMIN`; school media is `ROLE_ADMIN`-only; user photo is any authenticated role.
- **Entity images:** `School` (`logoMediaId`, `coverMediaId`), `Course` (`photoMediaId`), and `Program` (`photoMediaId`) reference public `Media` rows by FK instead of URL strings. Upload flow: `POST /api/v1/media?category=SCHOOL_LOGO|SCHOOL_COVER|COURSE_PHOTO|PROGRAM_PHOTO` (ADMIN-only) → read `MediaDTO.publicUrl` (a relative `/uploads/public/...` URL, set only on public media) → `PUT`/`PATCH` the entity with the media id. Response DTOs expose the resolved media as `logo`/`cover`/`photo` objects. Replacing an entity image removes the old media row at once and its file only after the transaction commits (`MediaService.deleteById` delegates to `deleteByIdsAfterCommit`, same contract as `deleteAllOwnedBy`: a rolled-back replacement, e.g. a duplicate code answering 409, keeps the old file); deleting a school removes the logo/cover rows and the photos of all its programs and courses (deleting a program: its own and its courses' photos), files again only after the commit, and clears its school and program wishlist links first; `V16` adds the FK columns (`ON DELETE SET NULL`) and drops the legacy URL columns.
- **Moderation:** moderated media starts `PENDING`; an admin sets `VERIFIED`/`REJECTED` (with optional reason) via `PATCH /api/v1/media/{id}/verification`. Status is informational — a `REJECTED` document is not functionally blocked.
- **Endpoints:** `POST /api/v1/media?category=...` (upload), `GET /api/v1/media/{id}` (download), `GET /api/v1/media/mine` (own media), `GET /api/v1/media?status=PENDING` (admin queue), `PATCH /api/v1/media/{id}/verification` (admin), `DELETE /api/v1/media/{id}` (owner/admin). Downloads render inline only for a MIME allowlist, else force `attachment`, and always send `X-Content-Type-Options: nosniff` + a sandbox CSP.
- **Migrations:** `V14`/`V15` create the `media` table and migrate legacy `users.diplomas`/`certificates`/`presentation_video_url` data; `MediaMigrationRunner` relocates pre-existing private files into `storage/private/` at startup. These run only against Postgres — the H2 test suite (Flyway disabled) generates the schema from the entity.

### Mail and tokens

- **Mail layer** (`mail/`): `EmailSender` port with `SmtpEmailSender` (`MAIL_ENABLED=true` + `SPRING_MAIL_HOST`/`MAIL_FROM`), `DisabledEmailSender` (default: nothing leaves the process) and `DevLogEmailSender` (`app.mail.dev-log`, local only, refused under `prod`). `EmailTemplates` builds fr/en messages; links are `app.frontend-base-url + /<lang>/verify-email#token=...` (fragment, never the request Host). Services publish `AccountEmailRequested`; `AccountEmailListener` sends it after commit on the bounded `mailExecutor`, so a mail failure never fails the request. `GET /api/v1/auth/capabilities` reports `emailEnabled`.
- **Delivery outcome, contact mail and providers**: `EmailSender.send` returns a `SendOutcome` (never throws, never leaks an address/host/secret; `SendOutcomeClassifier` reads exception types and SMTP codes only). The contact-form mail runs on its own bounded `contactMailExecutor` (`ContactEmailListener`: retries transient outcomes per `app.contact.mail.retry.*`, saves `PENDING -> SENT|FAILED|SKIPPED` + attempts via `ContactMailStatusService` in `REQUIRES_NEW`, `V27`); admins can `POST /api/v1/admin/messages/{id}/resend` (404, then 503 mail disabled, then 409 while the row is `PENDING`; one conditional UPDATE `claimResend`, a row PENDING longer than `app.contact.mail.pending-timeout` (15 min, `V28` `mail_pending_since`) is resendable again) and check SMTP with `POST /api/v1/admin/mail/test` (to their own address, 10 s cooldown; the dev-log sender answers `200 {"status":"LOGGED"}`, `SendOutcome.LOGGED`, which leaves contact rows `SKIPPED`: it never claims a delivery). The classifier reads SMTP codes: any 5xx is `REJECTED`, a 4xx without 5xx is `FAILED` (retried), because Angus lists a 451/421-refused recipient as valid-but-unsent. `MAIL_PROVIDER=brevo|gmail|ses|custom` only fills `spring.mail.*` defaults (`MailProviderEnvironmentPostProcessor`, registered in `META-INF/spring.factories`, only when `MAIL_ENABLED=true`); see `docs/production.md`.
- **Tokens**: `UserTokenService` issues single-use tokens (32 random bytes, Base64url, 43 chars) and stores only their SHA-256 hex in `user_tokens` (`V17`), with the purpose (`EMAIL_VERIFICATION`, `PASSWORD_RESET`), the address they were issued for and `issued_at`/`expires_at` from the injected `Clock`. Issuing an `EMAIL_VERIFICATION` token consumes the older open one of the user (a `PASSWORD_RESET` issue does not: otherwise anyone could kill the owner's live link by spending the address budget, and a successful reset burns the others); issuance is serialised per lower-cased address by `AddressIssueLock` (`pg_advisory_xact_lock` on Postgres, a striped in-JVM lock on H2) because the limits are check-then-insert; rows older than 7 days are purged lazily. Limits per (user, purpose): `app.tokens.cooldown-seconds` (60, only against tokens issued for the user's current address) and `app.tokens.max-per-day` (5) and `app.tokens.max-per-address-per-day` (3, per purpose, counted on `lower(email)` across all users, deleted accounts included: `user_tokens.user_id` is `ON DELETE SET NULL` so the rows survive until the 7-day purge; orphaned tokens cannot be consumed; `V18` index) raise `TooManyRequestsException` (429 + `Retry-After`); registration and profile updates swallow a refusal, only resend shows the 429. Any unusable token (unknown, expired, used, address changed) is the same `InvalidActionTokenException`: 400 `{"token":"Lien invalide ou expiré"}`.
- **Email verification is optional**: unverified accounts sign in normally. `POST /api/v1/users` (optional `lang` fr|en) sends the mail; `POST /api/v1/auth/email-verification/confirm` (public, POST so link prefetchers cannot burn it) -> 204; `.../resend` (Bearer) -> 202, 409 already verified, 429, 503 mail disabled. The address no longer changes through `PUT/PATCH /users/{id}` (a different `email` there is 400 `{"email": ...}`, the same one in any case is ignored): `EmailChangeService` does it in two steps, `POST /api/v1/users/{id}/email-change` (owner only, `{newEmail, currentPassword, lang}`, 202; 400 `{currentPassword|newEmail}`; 429; 503 while mail is disabled) stores nothing on the user and issues an `EMAIL_CHANGE` token bound to the NEW address (the cooldown and caps apply to that address) which is mailed there (`/<lang>/verify-email#token=...&type=change`); the old address keeps signing in until `POST /api/v1/auth/email-change/confirm` (public) swaps it, verified, and burns the other pending/verification links. `GET` returns `{pendingEmail}` (absent when none), `DELETE` cancels, `POST .../resend` mails the pending address again (409 when nothing is pending). A link whose address someone else took meanwhile is the usual `InvalidActionTokenException`. Confirmation increments the persisted credential version and deletes refresh tokens under the user lock in the same transaction. Every old access/refresh session is then refused; the web clears its local identity and invites sign-in with the new address. `V17` marks existing users verified; `AdminBootstrapRunner` marks the admin verified. No token is created while mail is disabled. Email uniqueness is enforced case-insensitively in code (registration and profile update answer 400 `{"email":...}`); there is deliberately no unique `lower(email)` index (existing data may hold case variants), so `findByEmailIgnoreCase` would throw if such duplicates already exist: residual risk, clean the data before adding the index.
- **Password reset**: `POST /api/v1/auth/password-reset/request` (`ForgotPasswordRequest`) always answers `202 {"status":"accepted"}` for a well-formed email (known, unknown, case variant, cooldown, capped, mail disabled): `PasswordResetService.request` looks the address up as a list (`findAllByEmailIgnoreCaseOrderByIdAsc`, oldest account wins, duplicates never throw), does dummy work for unknown addresses, swallows `TooManyRequestsException` and creates no token while mail is disabled. `POST .../confirm` (`ResetPasswordRequest`) -> 204; password length and confirmation are checked first (`FieldValidationException` -> 400 `{"field": message}`), then in one transaction the token is consumed (`PASSWORD_RESET`), the password is written with the targeted `UserRepository.updatePasswordAndRevokeSessions`, the credential version is incremented and other open reset/email-change tokens are burned, `RefreshTokenService.deleteByUserId` ends the sessions and `markEmailVerified` runs. Passwords are limited to 72 UTF-8 bytes (`@MaxUtf8Bytes`, BCrypt) on register, profile update and reset; changing the password through `UserService.patch` also burns outstanding reset tokens. Reset revokes existing access tokens through the persisted credential version. Self-service profile password changes require the current password and revoke access/refresh sessions too. Residual: the per-address reset budget can be exhausted by anyone (the owner then relies on links already sent or an admin reset), and an unknown address answers a few ms faster than a known one (Traefik per-IP limits). Both paths sit under `/api/v1/auth/**` (permitAll, no `WebSecurityConfig` change). `PasswordResetIntegrationTests` compares status, headers and body byte for byte across the cases.
- **One rating per user per target**: `school_rates`/`program_rates`/`course_rates` are unique on `(user_id, school_id|program_id|course_id)` (`V24`, which first deletes older duplicates keeping the latest `created_at`, then the highest id; mirrored by `@Table(uniqueConstraints)` so H2 matches). `POST /api/v1/{school,program,course}-rates` is an upsert: a second rating by the same user for the same target updates note/comment in place and answers **200** with the same id (first rating: 201). A lost insert race answers 409 (`ConflictException`) only when the violated constraint is one of the `uk_*_rates_*` (`UniqueRateViolation`); other integrity errors keep their usual handling. The rate controllers reset `id` and the audit fields right after mapping (`setId(null)`), because a client-supplied id would make `save()` merge into another user's row. `RateDTO.comment` is capped at 150 (the column length). When re-rating, a `null`/absent comment keeps the previous one (null = keep, like PUT elsewhere) and an empty string clears it. `UniqueRateViolation` reads Hibernate's `ConstraintViolationException.getConstraintName()` first and only falls back to scanning messages. Rows with a null target are not constrained. Validated on a throwaway Postgres 18 (V1..V23, seeded duplicates, V24, then a boot with `ddl-auto: validate`).
- **Expert approval**: `users.expert_status` (`PENDING|APPROVED|REJECTED`, `V29`; null for other roles) plus `expert_status_reason` (255) and `expert_decision_date`. A public teacher registration is `PENDING`; `@RequiresApprovedExpert` (`ExpertAccess`) guards program/course ratings and reads the status from the database on every request. Never map the status from a DTO (`ModelMapperConfig` skips it). `ExpertApprovalMigrationPostgresIntegrationTests` replays V1..V29 on a **throwaway** Postgres (it wipes the schema; refuses port 5432 and URLs containing "meetstudent"): `docker run -d --name mig-pg -e POSTGRES_PASSWORD=pw -e POSTGRES_DB=mig -p 127.0.0.1:55432:5432 postgres:18`, then `MIGRATION_PG_URL=jdbc:postgresql://127.0.0.1:55432/mig MIGRATION_PG_USER=postgres MIGRATION_PG_PASSWORD=pw ./mvnw verify -Dit.test=ExpertApprovalMigration* -Dtest=skip -DfailIfNoTests=false`, then `docker rm -f mig-pg`. Without the variables it is skipped.
  **Admin queue** (`AdminExpertController` / `AdminExpertService`, `/api/v1/admin/experts`, ADMIN only through `/api/v1/admin/**`): `GET ?status=PENDING|APPROVED|REJECTED` (paged like the contact messages: fixed order registration date desc then id desc, `?sort=` ignored, size capped at 100, `AdminExpertDTO` with id, names, email, `qualification`, `registeredAt`, `status`, `reason`, `decisionDate` and nothing else), `POST /{id}/approve` (clears the reason; also re-approves a rejected expert) and `POST /{id}/reject` (optional body `{"reason"}`: trimmed, blank = none, 255 max, control, invisible format (bidi, zero-width, BOM), line/paragraph separator and lone surrogate characters refused (tab/CR/LF kept; `SafeText`), 400 `{"reason": ...}`; also valid on an approved expert). 404 unknown user, **409 when the target is not `ROLE_EXPERT`**. The decision is a dedicated service method under the user row lock and never goes through `UserDTO`/`UserMapper`; the status is read live by `ExpertAccess`, so it applies to the very next request with the same token. Rejecting does **not** delete the ratings the expert already published. **Mails and idempotence**: `ExpertEmailRequested` (types `EXPERT_REQUEST_RECEIVED`, `EXPERT_APPROVED`, `EXPERT_REJECTED`) is published by `UserController` after a teacher registers (`PENDING`, language = the registration `lang`) and by `AdminExpertService` inside the decision transaction; `ExpertEmailListener` sends it AFTER_COMMIT on `mailExecutor`, so a send failure (logged by the sender as type/userId/outcome only) never fails the registration or the decision; `ExpertEmailTemplates` builds fr/en text + HTML to the user's own address only, with a fixed subject, the first name and the reason HTML-escaped (reason shown only when present, already `SafeText`-checked) and nothing else (no token, no link). The admin endpoints take an optional `?lang=fr|en` (French by default) because the user has no stored language. The decision is **idempotent**: approving an `APPROVED` expert or rejecting a `REJECTED` one answers 200 with the stored state, keeps the first date and reason and sends no mail; the mail goes out only on a real status change (reason validation still runs first, so a bad reason is 400 even on a repeat). Known limits: the back office does not send `?lang` yet (decision mails are French), the mails share the `mailExecutor` (2 threads, queue 100; a full queue drops one, arrival order is not guaranteed), and rejecting an already rejected expert with a new reason is ignored (200). **Role changes revoke sessions**: `UserService.applyAdminRole` increments `passwordVersion` and deletes the refresh tokens whenever the role actually changes (same role = nothing revoked), so a demoted admin or expert is refused (401) with the old token at once.
- **Forum** (`V33`, `ForumController` / `ForumService`, `/api/v1/forum`): `forum_threads` (title <=150, body <=5000, optional `school_id`, `locked`, `hidden`, `created_at`, `modified_at`) and `forum_replies` (flat, `thread_id` cascade); `author_id` and `school_id` are `ON DELETE SET NULL` (`@OnDelete`, so H2 matches), hence deleting an account or a school never touches `UserService`: the messages stay, `authorDeleted` is true and `authorName` absent (the client owns the "deleted user" text). **Reads are public** (`GET` `permitAll` in `WebSecurityConfig`): `GET /threads?schoolId=` (an unknown school = empty page), `GET /threads/{id}`, `GET /threads/{id}/replies`; fixed order newest first then id desc (`?sort=` ignored, size capped at 100, like the admin experts list); a thread carries `replyCount`. **Writes** use `@RequiresForumWriter` (`hasRole('STUDENT') or (hasRole('EXPERT') and @expertAccess.isApproved(...))`, status read live): anonymous 401, pending/rejected expert and admin 403 (same rule for edit/delete, even of their own old messages). `POST /threads` and `POST /threads/{id}/replies` -> 201; `PUT /threads/{id}` and `PUT /replies/{id}` (author only, `schoolId` ignored on edit, sets `modifiedAt`, counts in the write budget); `DELETE` -> 204 (deleting a thread deletes its replies); another user or an admin -> 403 (admin deletion lives in the moderation endpoints, below). Validation: `@NotBlank`/`@Size` on the records (surrounding whitespace stripped, nothing else altered) then `SafeText` (control, invisible, bidi, separators and the invisible fillers U+3164/2800/115F/1160/FFA0/180E refused, tab/CR/LF kept) -> 400 `{"title"|"body": ...}`; unknown `schoolId` on creation -> 400 `{"schoolId": ...}`; unknown or hidden thread/reply -> 404; **a locked thread refuses new replies with 409** (`ConflictException`; edits and deletes of existing own messages stay allowed). Plain text only: stored and returned as typed, JSON content type, never HTML. **Rate limit**: `ForumRateLimiter` (in memory, per user id, sliding window, `app.forum.rate-limit.max-per-window` 5 / `window-seconds` 60) counts thread and reply creations **and edits** together (5 writes per minute and per user), after validation, ownership and the lock check (invalid or refused requests and deletes do not consume it; deleting stays possible when the budget is spent); 6th write -> 429 + `Retry-After`. **Hidden messages** (`hidden`, set by the admin moderation endpoints, see below) are never returned to non-admins, body included, and cannot be edited/deleted by their author (404); an admin caller (`ROLE_ADMIN` authority) gets them with `hidden: true`. **DTOs** (`ForumThreadDTO`, `ForumReplyDTO`): id, text, `schoolId`/`schoolName`, `authorName` (first name only; `firstname` is `@Size(max=100)` and `@SafeName`, i.e. no hidden character, tab or line break, on `RegisterRequest` and `UpdateProfileRequest`), `authorRole` (`STUDENT`|`EXPERT`), `authorDeleted`, `mine` (computed server side, no user id is ever exposed), `locked`, `hidden`, `replyCount`, `createdAt`, `modifiedAt`; no e-mail, last name or user id. `ForumMigrationPostgresIntegrationTests` replays V1..V33 on a throwaway Postgres (same variables as the expert-approval one) and checks sizes, the FK actions and the school index (school_id, created_at DESC, id DESC).
- **Forum moderation** (`V34`, `ForumController` report endpoints, `AdminForumController` under `/api/v1/admin/forum`, `ForumReportService`, `ForumModerationService`): `forum_reports` (exactly one of `thread_id` / `reply_id` by CHECK, `reporter_id`, `reason` <=255, `target_snapshot` <=1000 (NOT NULL), `status` OPEN|HANDLED|DISMISSED, `created_at`, `handled_at`, `handled_by`; unique `(reporter_id, thread_id)` and `(reporter_id, reply_id)`). **Reporting**: `POST /api/v1/forum/threads/{id}/report` and `/replies/{id}/report`, body `{"reason"}` (`@NotBlank`/`@Size(255)`, stripped, then `SafeText` -> 400 `{"reason": ...}`), `@PreAuthorize("hasAnyRole('STUDENT','EXPERT')")`: any signed-in non-admin, expert pending or rejected included (anonymous 401, admin 403); 201 with no body; unknown or hidden message (a reply of a hidden thread too) 404; own message 409; already reported by the caller 409 (also when the earlier report is closed). Order of checks 404 -> 400 -> own 409 -> duplicate 409 -> rate limit, so refused requests never consume the budget. Races at insert are translated in `ForumReportService.save` into clean client errors (the global handler never sees them, but Hibernate and the driver still log the violation themselves, possibly at ERROR; the report budget is consumed before the insert, so such a 404/409 race costs one slot): foreign key violation (SQLSTATE 23503, message deleted between read and insert) -> 404, unique violation (23505, concurrent duplicate) -> 409. The report stores a **snapshot** of the reported text (first 1000 UTF-16 units, never splitting a surrogate pair). **Budget**: `ForumRateLimiter.checkReport`, own sliding window `app.forum.report-rate-limit` (10 per user and hour, 429 + `Retry-After`), separate from the 5 writes per minute (neither consumes the other; `ForumRateLimiterTest` was checked to fail when `checkReport` is wired to the writes window). **Admin** (`@PreAuthorize("hasRole('ADMIN')")` + the `/api/v1/admin/**` rule; anonymous 401, others 403): `GET /reports?status=` (all when absent; paginated, size <=100, fixed order `createdAt desc, id desc`, `?sort=` ignored; unknown status 400) returning `ForumReportDTO` (`id`, `targetType` THREAD|REPLY, `targetId`, `threadId`, `threadTitle`, `excerpt` = current text, `reportedExcerpt` = text when reported, both <=200 code points + `…`, `targetModifiedAt` (so "edited after the report" is visible), `targetHidden`, `reason`, `status`, `reporterName` first name only and absent once the account is deleted, `createdAt`, `handledAt`; never an e-mail, last name, user id or the closing admin); `POST /reports/{id}/handle|dismiss` (row lock; **idempotent**: a closed report is returned unchanged, first decision, `handledAt` and `handled_by` kept, no error; does not touch the message; the DTO is built inside the transaction, no open-in-view needed, covered by a test with `spring.jpa.open-in-view=false`); `POST /threads/{id}/hide|unhide|lock|unlock` (-> `ForumThreadDTO`, `replyCount` including hidden), `POST /replies/{id}/hide|unhide` (-> `ForumReplyDTO`): **idempotent** (second call changes nothing, 200), 404 if unknown, work on hidden messages; `DELETE /threads/{id}` and `/replies/{id}` (204, final): **not idempotent, a second delete answers 404**; **an admin never edits someone else's text** (the author-only `PUT` stays 403 for admins). Hiding a thread does not close its reports and closing a report does not hide anything. **Report lifecycle (decided)**: `thread_id` / `reply_id` are `ON DELETE CASCADE` (deleting a reply, or a thread and so its replies, by the author or the admin, removes their reports, handled ones included), `reporter_id` and `handled_by` are `ON DELETE SET NULL` (deleting the reporter's account keeps the report, anonymous; NULLs are distinct so several anonymous reports on one message coexist). **Row locks / lost updates**: every writer of `hidden`, `locked` or a message's text (`hideThread|Reply`, `lockThread`, the author's `updateThread|Reply` and deletes) and `createReply` load the row with `findByIdForUpdate` (`PESSIMISTIC_WRITE`, SELECT ... FOR UPDATE), and `ForumThread`/`ForumReply` are `@DynamicUpdate`, so concurrent transactions queue on the row and work on the committed state: an author's edit cannot undo a hide, a hide cannot undo a lock, no reply is accepted after a lock committed, an edit started during a hide finds the message hidden (404). `ForumLockRaceIntegrationTests` (6 cases, `ForumRaceSupport`) holds one transaction open and waits, without sleeping, until the second one is parked on the lock (H2, `LOCK_TIMEOUT=10000` in the test URL); `ForumReportsMigrationPostgresIntegrationTests` replays V1..V34 on a throwaway Postgres (CHECK 23514, unique 23505, length 22001, cascades thread -> replies -> reports, SET NULL, queue index) and checks on the real engine that a second `SELECT ... FOR UPDATE` waits (`pg_stat_activity` `Lock`) and then sees the committed lock (the SQL, not the Spring code, runs against Postgres).
  Known limits (accepted): deleting a message erases its reports and their history (no audit trail); one report per user and message, even when closed, so a user cannot report again after the message was edited (the snapshot and `targetModifiedAt` let the admin judge); no grouping of reports, so fake accounts can flood the queue (a per-target counter is a follow-up for forum/04); a locked thread still lets authors edit and delete their own messages (decision); replies to one thread queue on its row for the length of their short transaction; a very rare deadlock is possible between an account deletion (its `ON DELETE SET NULL` locks the user's messages) and that user's reply to his own thread, and likewise between closing a report (`ForumReportService.close`, `handled_by`) and the deletion of the administrator account doing it; Postgres answers 40P01, the request fails with 500, a retry works; the rate limiters are in memory (one API instance, reset on restart).
- **Brute-force limits** (`CredentialAttemptLimiter`, in memory, one API instance, reset on restart): sign-in (wired by wrapping the `AuthenticationManager` in `WebSecurityConfig`) is always keyed by the NFKC upper-cased address (stored as SHA-256) and, when `findAllByEmailIgnoreCaseOrderByIdAsc` finds an account, also by its id (locked if either key is, failures count on both): every spelling the DB `upper()` folds to the account (e.g. `ſ`->`S`, `ı`->`I`) shares one budget, and a spelling only NFKC folds (fullwidth `ａ`) locks known and unknown addresses alike (same query, same answers), and every `currentPassword` check (`EmailChangeService.request`, `UserService` delete and password change; a missing password is a 400 that does not count) by user id, in two separate namespaces. 5 consecutive failures lock the key 1 min, the next streak 5 min, then 15 min (cap); a success resets, a day without failure forgets; attempts in flight count, other errors do not. While locked the password is not checked: 429 `ErrorResponse` "Trop de tentatives, réessayez plus tard" + `Retry-After`, identical for unknown emails. Memory: at most 50 000 never-locked keys per namespace (LRU) plus locked/escalated keys kept apart, never evicted by a flood of new keys, up to a hard cap of 200 000 (oldest lock dropped first), and a sweep every minute (Traefik `rl-auth` stays the per-IP limit).
- **Forum and email verification**: `@RequiresForumWriter` also requires `emailVerified` while `MAIL_ENABLED=true` (`app.mail.enabled` only; the local dev-log sender does not turn it on, so locally it can differ from `GET /auth/capabilities` `emailEnabled`), read live by `ForumWriterAccess`; otherwise 403 like the other refusals, for students and approved experts alike, edits and deletes of own messages included. Reading and reporting are unchanged.
- **Tests**: integration tests that rely on the after-commit mail must be non-transactional and `@Import(CapturingMailConfig.class)` (`CapturingEmailSender.last()` / `extractToken`). H2 never runs `V17`; validate migrations against Postgres with `ddl-auto: validate`.

Residual risks of the mail limits (accepted): an attacker can pre-consume the address budget of a future user (verification is optional, so low impact); plus-addressing and dots make different addresses for the cap; DB uniqueness on `users.email` is still case-sensitive (case-insensitivity is enforced in code only, so two concurrent case-variant registrations can both succeed).

### Production

The `prod` profile (env vars, admin bootstrap via `AdminBootstrapRunner`, proxy headers, disabled Swagger) is documented in `docs/production.md`. Access token lifetime is `security.jwt.access-ttl-minutes` (`JWT_ACCESS_TTL_MINUTES`, default 60); invalid/expired refresh tokens raise `InvalidRefreshTokenException` (HTTP 401).

### First admin and development seed

- `AdminBootstrapRunner` runs on every profile except `test`. `prod` requires `ADMIN_EMAIL` + `ADMIN_PASSWORD` (12+ chars) and aborts startup without them; `dev`/`docker` treat them as optional: with neither set the seeded `admin@meetstudent.com` / `password` row is left alone, with both set a new admin is initialized (or the unchanged published seed is reclaimed) and the seeded default hash is neutralised exactly as in production; setting only one is an error. An existing admin password is preserved across restarts; changing `ADMIN_PASSWORD` no longer rotates it. Existing non-admin accounts cannot be promoted by bootstrap. Seed credential changes revoke sessions and action links. `app.admin.*` lives in `application.yml`.
- `config/seed/DevSeedRunner` (profiles `dev` and `docker` only, never `prod`/`test`) loads `src/main/resources/seed/senegal.json` (`SeedData`): tags, accreditations, schools, programs, courses and program/accreditation links, **no users and no ratings**. It is additive and idempotent (natural keys: tag name, accreditation code, school name, program name within the school, course name within the program) and never edits existing rows. The shipped file is a sourced core set (every school carries a `source` URL): public universities at faculty/UFR level, UADB at degree level, the ISEP network, major private institutions, notable lycées. The model has no school type, so the type lives in tags. It deliberately omits what could not be sourced (most private institutes, vocational centres, courses, accreditation links: they need start/end years). `SeedDataFileTest` guards the file against the schema limits (name <= 50, code <= 5, no duplicates).

### Testing

Tests live in `src/test/java/com/bowe/meetstudent/` split into `unit/` (Mockito) and `integration/` (MockMvc + H2).

- Test config (`src/test/resources/application.yml`) disables Flyway and uses `ddl-auto: create-drop` with H2 in `MODE=PostgreSQL`.
- **Authentication in tests:** do NOT use `jwt().authorities(...)` from `SecurityMockMvcRequestPostProcessors` — the generic principal causes a `ClassCastException` against the custom `UserPrincipal`. Use `TestDataUtil.mockUser(String role)`, which builds a `UserPrincipalAuthenticationToken` with a valid `UserPrincipal`.
- Integration tests must use the full versioned path (`/api/v1/schools`, not `/api/schools`).

### Feature workflow

When adding a feature: entity → repository → service → DTOs → mapper → controller (with Swagger annotations) → Flyway migration → unit/integration tests. Create a working branch from `dev` for features and bug fixes, then open the PR back to `dev`.
